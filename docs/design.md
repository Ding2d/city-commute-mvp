# 需求、设计约束与第二阶段计划

## 来源与边界

根据用户提供的“获取经典通勤路线”历史对话和本次任务：数据应开放免费、易获取，目标是任意中国城市 3–5 条代表性地点对，兼顾居住区→就业区、枢纽→商务区、枢纽→地标等情景。历史记录中的助手正文为引用占位符，无法恢复；没有据此推断额外技术承诺。
独白描述模拟人物、出行目的、可能难点，默认 6 句、20–30 汉字/句；参数可调。
第一阶段交付可直接执行的 Python 命令行项目和完整 Mock 流程；不承诺任意城市已有可信路线，不提供导航。

## 架构

命令行参数校验与城市名称规范化 → DataProvider 产生城市与候选 → 规则评分和场景覆盖 → NarrativeProvider 逐条生成并校验 → 显式来源/模拟标记的结果，终端显示易读文本并保存 JSON。
Mock 不依赖 GIS 重型库。OSMnx、GeoPandas、Shapely、NetworkX 列为可选 `geo` 依赖，第一阶段无需安装。真实 provider 独立存放且暂未实现，禁止用 Mock 冒充真实数据。
种子库按城市保存地点对，人物/目的/难点由规则模板赋予；没有坐标与真实换乘推断。新增城市种子只需增加五个按模板顺序排列的地点对；第二阶段应改为带类型、实体 ID 与证据的结构化种子。
城市模型中的 `identity_verified=false` 表示名称未经过城市实体解析；输入汉字校验只限定形式。

## 第二阶段实施顺序

1. **城市解析与证据结构**：用 Wikidata 城市实体 ID、行政区及 OSM 城市边界解析名称和同名城市；区分行政市/中心城区。增加坐标、实体来源 ID、抓取时间、数据许可、缓存版本、端点核验和路径核验各自独立的字段。
2. **Wikidata 语义获取**：通过 SPARQL 查询边界/范围内的车站、地标、高校与就业相关实体，补充 OSM 语义。实体缺失很常见，无法查询到就业区时用人工种子补充并记录依据，不能声称有 Wikidata 的全面覆盖。
3. **OSM 获取与缓存**：先用小范围 Overpass 获取地点与交通标签，设超时、限流、退避、磁盘缓存；扩展时使用区域离线提取文件。所有请求配置集中化，记录源数据时间。不要在每次脚本执行时全城下载道路。
4. **地点对匹配与候选生成**：将 OSM/Wikidata 实体按名字、空间距离和类型匹配，用居住→就业、枢纽→地标等模板生成候选。过滤同点、类型错误与跨城区不合理组合，保留匹配置信度和证据。
5. **路径可行性**：用 OSMnx/NetworkX 计算步行/道路连通性，Shapely/GeoPandas 做边界和空间过滤。OSM 关系不等于完整公共交通时刻表；有可用且许可兼容的 GTFS 后再引入公交路径计算，缺失时仅返回地点对或道路路径，不能声称已核验地铁换乘、班次和通勤耗时。
6. **评分替换**：以实体可识别性、场景合理性、空间跨度、路径证据与覆盖多样性构建可解释分数，替换 Mock 常量。开放地图和规则不能证明真实客流“经典”，标签应继续使用“代表性候选”。允许用户/人工评审种子及候选。
7. **叙事约束**：区分有证据的路线属性和可能难点；将证据白名单送给 LLM。模型不得补充未知站名、出口编号或高峰拥堵事实。继续验证输出长度，并加事实引用检查、缓存和费用限制。
8. **集成验证**：先对四城市每城 3–5 条进行人工地点/路径核验，保存可回放小型数据 fixtures；再选无种子的城市验证泛化。测试 HTTP 超时、限流、空结果、实体歧义、缓存、坐标系和无公共交通数据时的降级行为。

## 验收与数据许可核查

- 任意输入城市先完成实体解析；不能解析时返回明确错误或未核验状态。
- 核验的地点/道路路径与模拟人物/独白分别标注证据；路径核验不能自动证明通勤代表性。
- 所有外部数据调用能缓存和复现，离线测试不访问公共端点。
- 接入时核查 OSM ODbL 归属与衍生数据要求、Wikidata CC0 和公共查询服务使用规则；开放数据不意味着托管端点无限免费可用。公共交通补充数据单独记录许可，不默认拥有免费完整 GTFS。
- 第一阶段不启用外部数据请求；第二阶段开始前核对上述服务的最新文档和政策。
